# Real VIPR v1.0 benchmark corpus

This directory contains 26 exact-SCIP certificates derived from published
mixed-integer programming benchmark sets. Every command below is run from the
repository root.

| Result class | Certificates | Source |
|---|---:|---|
| `RTP infeas` | 20 | ALU instances used in exact-MIP experiments |
| `RTP range` | 6 | ALU and MIPLIB 3.0 instances |

The checked-in `.mps` files are the solver inputs. The `.vipr` files were
generated by official SCIP 10.0.3 with `exact/enable = TRUE` and are the exact
files measured in `benchmarks/results/checker.csv`. `manifest.csv` records each
certificate's source family.

## Selection

Selection was completed before checker timing:

- Infeasibility: the first 20 emitted and accepted ALU certificates in family
  order whose raw VIPR files are below 5 MB.
- Range: published ALU/MIPLIB 3.0 instances that finish exact-SCIP generation
  within 120 seconds, produce a VIPR file below 20 MB, and pass the strict v1.0
  result checker.

The caps keep the workshop artifact practical and exclude cases such as
`alu5_8`, whose certificate is 32.6 MB. Rejected or incomplete solver output is
not reported as a successful benchmark.

## Rechecking

Build the checker and check every certificate:

```bash
lake build viprcheck
find benchmarks/infeas benchmarks/range -name '*.vipr' -exec \
  .lake/build/bin/viprcheck --native-mode full {} \;
```

The expected result is 26 accepted certificates.

Run the verified array-backed checker timing matrix:

```bash
python3 benchmarks/run_compiled.py \
  --modes full slice \
  --output benchmarks/results/checker.csv
```

For each infeasibility certificate the script records complete replay and
dependency-sliced replay. Range certificates use complete replay
because kernel reconstruction is currently implemented only for infeasibility.

The array-backed implementation is the sole executable checker. It is proved
directly sound against the declarative proof system by
`checkVipr_refines` and `checkVipr_sound`; there is no executable
list-based checker or checker-equivalence layer.

The raw solver certificates all contain the incomplete-format `lin weak`
record. To measure the official C++ tools, first build both `viprcomp` and
`viprchk`, then run:

```bash
python3 benchmarks/run_cpp.py \
  --completer /path/to/viprcomp \
  --checker /path/to/viprchk
```

The runner uses one completion thread with SoPlex disabled, as only weak
derivations occur, then checks the completed file. With scipopt/vipr `master`
(`99eec19`) the official pipeline accepts all 26 files. (At the earlier commit
`30f2951`, `viprcomp` returned success for 13 files but produced completions that
`viprchk` rejected.) `benchmarks/results/cpp.csv` records each outcome rather than treating a
failure as a successful timing.

Certificate generation, parsing, and compiled execution are outside the
kernel-only trust boundary. These measurements evaluate checker performance;
the Lean soundness theorems establish what acceptance means.

## Results

The artifact includes 20 infeasibility certificates from the published ALU
suite and 6 objective-range certificates from ALU/MIPLIB 3.0. All are genuine
official exact-SCIP 10.0.3 output.

Measured as one warmed run on an Apple M3 Pro (12 cores, 36 GB), Lean 4.35.0,
macOS 26.7.1. These are compiled CLI timings and are not kernel certification.

**The runners pin `VIPRCHECK_TASKS=1`.** Upstream `viprchk` is single-threaded,
so a parallel LeanVIPR against a sequential `viprchk` would not be a comparison
of checkers but of core counts. Every number in this section is therefore one
core against one core. To measure the parallel replay instead, pass
`--lean-tasks N` to `run_new.py`, and compare against
`viprchk_parallel` rather than `viprchk` — upstream ships both.

Note also that the parallel replay trades CPU for wall clock: it costs roughly
4x the total CPU on step-heavy certificates, from atomic reference counting on
the pool the tasks share. Wall-clock tables will flatter it and CPU-time tables
will not, so say which is being reported.

## Kernel-mode results

Kernel mode emits the parsed certificate as Lean data and has the kernel reduce the
checker over it, yielding a machine-checked theorem. It is minutes per certificate
rather than seconds, so it is measured separately and with a 300 s cap:

```bash
python3 benchmarks/run_kernel.py --output benchmarks/results/kernel.csv
```

18 of 21 runs complete within the cap.
The three that do not are `kernel-full` on range certificates (`egout`, `flugpl`,
`gt2`), where there is no reconstruction path and the whole certificate must reduce.

| Certificate | Mode | Wall |
|---|---|---:|
| `alu4_5` | kernel-reconstruct | 61.6 s |
| `alu4_6` | kernel-reconstruct | 62.8 s |
| `alu6_5` | kernel-reconstruct | 80.6 s |
| `alu5_5` | kernel-reconstruct | 116.7 s |
| `alu7_6` | kernel-reconstruct | 136.3 s |
| `alu5_6` | kernel-reconstruct | 255.2 s |

These are two to three times faster than the same measurements before the
normalization and tokenizer work, and two certificates that used to exceed the cap now
complete: `alu5_5` went from a 300 s timeout to 116.7 s and `alu5_6` from a timeout to
255.2 s. That was not the expected direction -- `Array` is a `List` to the kernel, so
the dense normalization degrades there -- but less total work outweighs it. `alu7_6` is
the one regression, 100.6 s to 136.3 s.

Per-certificate numbers are in [`results/kernel.csv`](results/kernel.csv).
## The 112-certificate corpus

The 26 certificates above are checked in under `benchmarks/infeas/` and
`benchmarks/range/`, so they need no download.

A larger corpus of 112 published VIPR v1.0 certificates (about 18 GB gzipped) is
not stored in git. It contains:

- the 56 numerically easy and 50 numerically difficult MIPs from the
  [scipopt/vipr experiments](https://github.com/scipopt/vipr/tree/master/experiments)
- 3 Chvátal's-conjecture proofs
- 3 forged or manipulated certificates

Download it into `benchmarks/new/`. Each file is checked against the SHA-256
in [`benchmarks/new/manifest.csv`](new/manifest.csv):

```bash
python3 benchmarks/download_new.py                          # all 112; skips files already present
python3 benchmarks/download_new.py --sets negative chvatal  # or a subset
python3 benchmarks/download_new.py --verify                 # re-hash what is on disk
```

The reference C++ checker `viprchk` is built from
[scipopt/vipr](https://github.com/scipopt/vipr) at `99eec19` into the ignored
directory `viprcheck/`. It needs a C++ compiler, CMake, GMP and Boost (on macOS:
`brew install cmake gmp boost`):

```bash
git clone https://github.com/scipopt/vipr.git viprcheck
git -C viprcheck checkout 99eec19
cmake -S viprcheck/code -B viprcheck/code/build -DCMAKE_BUILD_TYPE=Release -DVIPRCOMP=OFF
cmake --build viprcheck/code/build --target viprchk
```

The 26 checked-in certificates contain `lin weak`, so their C++ pipeline
([`run_cpp.py`](run_cpp.py)) also needs `viprcomp`. To
build it, configure with `-DVIPRCOMP=ON`, which requires SoPlex. The 112
downloaded certificates are complete, so they need only `viprchk`.

Run `viprchk` and both Lean modes on every downloaded certificate, one process
at a time. Run this inside `tmux` or `screen`, because the whole corpus takes
many hours:

```bash
lake build viprcheck
python3 benchmarks/run_new.py --sets easy hard chvatal negative \
  --workdir /tmp/vipr-work --slice-all
```

The runner writes one CSV per method to `benchmarks/results/`: `new_cpp.csv`,
`new_lean_full.csv` and `new_lean_slice.csv`. It records the environment in
`new_env.csv` and writes per-run logs to `benchmarks/results/new_logs/`. Pass
`--resume` to continue an interrupted run, or create
`benchmarks/results/new_STOP` to stop after the current certificate. Without
`--slice-all`, slice mode runs only on `RTP infeas` certificates; for the other
certificates `viprcheck` falls back to complete replay anyway. The defaults are
a 1-hour timeout and an 18 GiB RSS / 32 GiB memory-footprint limit per check.
